  - **types Kysely** après une migration, depuis Bash dans `apps/server` : `npx kysely-codegen --dialect mysql --url "$DATABASE_URL" --out-file src/platform/kysely/schema.generated.ts` (le script `pnpm run db:codegen` passe par cmd.exe sous Windows, qui ne développe pas `$DATABASE_URL`) ; ils sont à jour au 13/10/2026 (complétés à la main depuis P5 : à vérifier par une génération si un doute survient) ;
  - **seeds** : `cd db && npx tsx seeds/run.ts` sur la base de test **et** de développement après toute modification ; rejouables sans effet destructif (insertion des absents ; rôles, permissions et attributions mis à jour ; une valeur de paramètre déjà semée ne change que par `SYSTEM_SETTING_REVISIONS`) ; `db/tests/seed.test.ts` vérifie **123 permissions et 500 attributions** (les assertions font foi) et **exactement 9 emplacements virtuels**.
- **Pièges connus** :
  - la base de test est **partagée et persistante** : chaque test crée ses propres données ; les paramètres système n'ont pas de fin de validité (la valeur la plus récente ≤ instant l'emporte) → valeurs stables ou datées au plus près ; une politique de contrôle de test doit avoir une fenêtre `validFrom`/`validTo` courte (la plus récente l'emporte) ;
  - tests à date fixe et tests relatifs à l'heure réelle cohabitent : les fenêtres hors ligne (30 jours, 7 jours) sont évaluées par la base à l'heure réelle ;
  - **politiques de contrôle et date réelle** (08/10/2026 : `production-sync-projections` échouait de 12 h à 15 h 40 UTC) : `currentPolicies` retient la politique de `valid_from` le plus récent parmi **toutes** les actives du type, quel que soit leur test d'origine. Une politique laissée sans fin par un test à date fixe devance donc celle d'un test relatif à l'heure réelle le jour où la date réelle l'atteint. Règles : un test à date fixe borne sa politique à sa journée (`validTo`) ; un test relatif à l'heure réelle date la sienne **à l'instant de l'opération qui la consulte** (si les opérations s'étalent sur plusieurs jours, il retire les politiques du type le temps du fichier) et la neutralise en `afterAll` (`neutralizePolicy`) ; pour retirer puis restaurer, toujours `withoutActivePolicies` / `retireActivePolicies` (`apps/server/test/helpers.ts`), qui remettent `status` **et** `valid_to` d'origine — remettre `valid_to` à `null` transformait les politiques bornées des autres tests en politiques sans fin ;
  - **paramètres système et date réelle**, même mécanisme et sans remède : une version n'a pas de fin et ne peut être ni modifiée ni supprimée (déclencheurs `no_update` / `no_delete`, BR-ADM-015). Un test relatif à l'heure réelle date ses paramètres une seconde avant l'opération qui les lit ; une exécution à l'heure réelle un jour J **empoisonne durablement** les tests à date fixe de ce jour (calibres d'œufs : `production-egg-collection-commands` au 22/10, `production-acceptance` au 28/10). **Ne jamais décaler l'horloge d'un test vers le futur sur la base partagée** (l'insertion est définitive) ; pour simuler une date, utiliser une base jetable ;
  - **fuseau des connexions** (12/10/2026) : le serveur (`createDatabase`) et le paquet `db` (`connectUtc`, `poolUtc`, `db/seeds/connection.ts`) ouvrent leurs connexions en UTC (pilote `timezone: 'Z'`, session `time_zone = '+00:00'`). Avant ce correctif, un poste en UTC+1 écrivait l'heure locale : une base créée avant le 12/10 garde des horodatages décalés d'une heure et la vérification du chaînage d'audit (`chain-verification`) y voit une rupture sur ses entrées antérieures, jusqu'à la fin du jour métier en cours. Toute nouvelle connexion MySQL (script, test) passe par ces aides ;
  - pour les éditions complexes, écrire un script dans un fichier temporaire plutôt qu'un heredoc (les accents graves et `${}` tronquent les heredocs) ;
  - avertissements Git « LF will be replaced by CRLF » : sans conséquence.
  - **identifiants d'amorçage** : tout `id` créé par `db/seeds/*.ts` est un UUIDv7 (`db/seeds/uuidv7.ts`) ; le serveur refuse les jetons dont `sub`, `device_id` ou `session_id` ne l'est pas (`MALFORMED_CLAIMS`). Une base de développement créée avant le 08/10/2026 peut contenir un administrateur local à identifiant non conforme : le désactiver (`UPDATE identity_users SET status='DEACTIVATED', status_reason=…, phone=…`) puis relancer `create-local-admin` ;
  - **renouvellement de session côté PWA** : `ensureAccessToken` ne lance qu'un renouvellement à la fois (le jeton de rafraîchissement tourne à chaque appel et sa réutilisation est refusée) ; tout nouvel écran qui appelle l'API passe par `authorizedRequest`, jamais par `fetch` direct ;
  - une migration **modifiée sur place** après avoir été appliquée n'est pas rejouée par dbmate : comparer une base reconstruite depuis les migrations à la base de test en cas d'échec inexpliqué d'une contrainte (`SHOW CREATE TABLE`).
