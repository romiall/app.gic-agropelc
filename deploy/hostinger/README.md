# Mise en ligne sur Hostinger (`app.gic-agropelc.com`)

Ce dossier reprend, sous forme de scripts versionnés, la procédure faite à la main le 26 et le 27/10/2026 depuis Anti-Gravity. Il ne contient **aucun secret** : la clé SSH reste dans `%USERPROFILE%\.ssh`, le fichier `.env` reste sur le serveur.

## Utilisation

Depuis la racine du dépôt, dans PowerShell (une seule ligne) :

```powershell
powershell -ExecutionPolicy Bypass -File deploy\hostinger\deploy.ps1
```

- **Livrer depuis une copie propre** : `build-bundle.ps1` (appelé par `deploy.ps1`) construit le paquet du dépôt qui contient le script, et **refuse** de le faire si des fichiers suivis de `apps`, `packages`, `db` ou `deploy` sont modifiés (le paquet ne correspondrait à aucun commit : une autre session peut avoir des changements non commités dans le même dossier) ou si `apps\pwa\dist\sw.js` manque (la livraison du 03/11/2026 est partie sans : `/sw.js` renvoyait la page d'accueil et aucun appareil ne pouvait se mettre à jour). Usage : `git worktree add --detach C:\gic-livraison <commit>`, `pnpm install`, `pnpm run build`, puis `deploy.ps1 -SkipBuild` depuis ce dossier ; `-AllowDirty` passe outre, sciemment. Les chemins du paquet (`%TEMP%`) sont communs à tous les dépôts : ne pas lancer deux constructions à la fois.
- `-BuildOnly` construit le paquet sans rien envoyer (`%TEMP%\gic-app-bundle.tar.gz`, taille et empreinte affichées).
- `-SkipBuild` réutilise la construction existante ; `-NoDbBackup` ignore la sauvegarde de la base (à n'utiliser qu'après une sauvegarde faite dans hPanel).
- `node deploy/hostinger/migrate.mjs --dry-run --since 20261201090600` affiche, sans connexion, le SQL que le serveur exécuterait pour les migrations plus récentes que la version donnée.
- `node deploy/hostinger/test-mariadb-compat.mjs` compile des requêtes Kysely sans base et vérifie que la couche de compatibilité MariaDB réécrit bien `CAST(? AS JSON)` et `FOR SHARE` (à relancer si Kysely est mis à jour).
- `import-reporting-commercial.mjs` (avec `reporting-import-mapping.mjs` et `mariadb-compat.mjs`, sur le serveur ou en local avec `tsx`) reprend le classeur de reporting du responsable commercial (194 prospects, 58 contacts) par les vraies commandes, avec essai à blanc, sauvegarde préalable de la base et vérification ligne à ligne : mode d'emploi, correspondance colonne par colonne et limites dans [`IMPORT-REPORTING-COMMERCIAL.md`](IMPORT-REPORTING-COMMERCIAL.md) ; essai de la correspondance : `node deploy/hostinger/test-reporting-import-mapping.mjs`.
- `node --env-file=.env grant-test-access.mjs <e-mail ou téléphone> [--days 30] [--dry-run]` (sur le serveur, dans le dossier de l'application ; `--dry-run` n'écrit rien) accorde, pour une durée limitée (1 à 90 jours), les rôles du système de portée globale qu'un compte n'a pas encore, pour qu'il puisse essayer toutes les fonctions. Chaque octroi porte une date de fin (l'accès s'éteint seul, ou se retire avant dans l'écran des comptes), passe par les contrôles de la commande `identity.role_assignment.grant`, laisse une ligne d'audit et invalide le cache des droits par événement. Les rôles de terrain (site, zone, équipe) ne sont que listés : ils exigent une organisation qui n'existe pas encore en ligne (0 site, 0 zone, 0 équipe au 30/10/2026).

## Ce que fait la mise à jour

1. Construction locale (`pnpm run build` : paquets partagés, serveur, PWA), compilation des semis en CommonJS, assemblage du paquet.
2. Envoi par `scp`, puis `remote-update.sh` sur le serveur :
   1. extraction du paquet dans `releases/<horodatage>/new` ;
   2. sauvegarde de la base (`mysqldump`) dans `~/backups_db/gic-<horodatage>.sql.gz` (les cinq plus récentes sont gardées, la nouvelle comprise ; ni `daily/` ni les copies faites à la main ne sont touchés) ;
   3. mise en place des nouveaux fichiers ; **l'ancienne version est gardée** dans `releases/<horodatage>/previous` ;
   4. **contrôle de compatibilité SQL** (`compat-check.mjs`) sur la base réelle, dans une table temporaire : écriture et relecture d'une colonne JSON avec le vrai `jsonValue` du code construit, verrous en partage et en écriture ; un échec annule la mise en ligne avant toute migration ;
   5. migrations (`migrate.mjs`, seulement celles qui ne sont pas dans `schema_migrations`) ;
   6. semis (réglages, règles d'alerte, droits : idempotents) ;
   7. redémarrage de Passenger (`tmp/restart.txt`) ;
   8. contrôle : `/health/ready` et la page d'accueil répondent 200 ; la route de connexion répond 401 à un identifiant fictif (une erreur 5xx annule la mise en ligne) ; les erreurs que le serveur a écrites dans `stderr.log` depuis le redémarrage sont comptées et affichées en avertissement.
3. En cas d'échec à l'une de ces étapes, le script **remet l'ancienne version** et la redémarre. Les migrations déjà appliquées restent (elles sont écrites pour rester compatibles avec la version précédente) ; la sauvegarde de la base reste dans `~/backups_db`.

Seules les cinq dernières livraisons sont gardées dans `releases/`.

## Retour arrière manuel

```bash
cd ~/domains/gic-agropelc.com/nodejs-app

```

## Adaptations à MariaDB et à l'hébergement

- Les lignes `GRANT` / `REVOKE` vers `gic_app` sont retirées des migrations (`migrate.mjs`) : l'hébergement n'a qu'un utilisateur.
- `DROP CHECK` devient `DROP CONSTRAINT` (syntaxe MariaDB).
- Dans les semis compilés, `CAST(? AS JSON)` devient `JSON_EXTRACT(?, '$')` (MariaDB ne connaît pas `CAST(… AS JSON)`).
- `dbmate` n'existe pas en ligne : `migrate.mjs` écrit dans la même table `schema_migrations`.
- **À l'exécution** (`mariadb-compat.mjs`, installé par `server.js` avant la création de l'application) : `CAST(? AS JSON)` devient `JSON_EXTRACT(?, '$')` (toute écriture d'une colonne JSON passe par `jsonValue()` : audit, événements, journal des commandes, tâches, alertes) et `FOR SHARE` devient `LOCK IN SHARE MODE` (plus de vingt-cinq lectures verrouillantes : caisse, quotas, coûts, transferts). La réécriture se fait à la compilation des requêtes Kysely : le code source et son comportement sous MySQL 8.4 ne changent pas, la suite d'essais n'est pas concernée. Essai local : `test-mariadb-compat.mjs` ; essai sur la vraie base avant chaque redémarrage : `compat-check.mjs` (AV-485).

## Opérations planifiées : sauvegarde tous les deux jours (cinq copies), copie hors hébergement, purge des alertes, essai de restauration

Écrit et éprouvé **en local le 05/11/2026** ; **copié sur le serveur le 06/11/2026**, à la demande du porteur (`install-ops.ps1` : `backup-db.sh`, `backup-rotate.mjs` et `purge-alerts-cron.sh` dans `~/gic-ops`, droits 700 pour les deux scripts shell). **Aucune tâche cron n'est créée** (à faire dans hPanel > Avancé > Tâches Cron) : aucune sauvegarde périodique ne tourne donc encore. **Premier essai sur l'hébergement fait le 07/11/2026**, à la demande du porteur, dans l'environnement minimal d'une tâche cron (`env -i`, `PATH=/usr/bin:/bin`) : sauvegarde `gic-daily-20261107-062025.sql.gz` de 2,2 Mo (159 tables), contrôles, rotation (« 1 gardée, 0 supprimée ») et journal corrects, droits constatés (dossier `daily/` en 700, sauvegarde, `latest.txt` et `backup.log` en 600) ; `~/backups_db` pèse alors 15 Mo, dont 9 sauvegardes d'avant livraison. Jusqu'ici la seule sauvegarde de la base était celle que `remote-update.sh` fait avant chaque livraison (`~/backups_db/gic-<horodatage>.sql.gz`) : aucune entre deux livraisons, aucune copie hors de l'hébergement.

**Politique de conservation (décision du porteur du 07/11/2026, pour limiter l'espace occupé en ligne)** : **une sauvegarde tous les deux jours, cinq copies au plus** (dix jours d'historique) ; après chaque ajout, la plus ancienne au-delà de la cinquième est supprimée (la nouvelle écrase la plus ancienne). Les sauvegardes faites avant chaque livraison (`~/backups_db/gic-<horodatage>.sql.gz`) sont plafonnées de la même façon (cinq gardées, la nouvelle comprise, à chaque livraison). Une base de 2 Mo compressés occupe ainsi une dizaine de Mo ; pour une base N fois plus grosse, comptez 5 × N × 2 Mo pour les sauvegardes périodiques. **Ne sont pas sauvegardées** : les photos jointes (rangées sur le disque du serveur, hors base).

Essai de restauration (poste local avec un client `mysql` ; le mot de passe va dans un fichier d'options que le porteur crée lui-même, jamais dans une commande) :

```powershell
node deploy\hostinger\restore-check.mjs "$env:USERPROFILE\gic-backups\gic-daily-AAAAMMJJ-HHMMSS.sql.gz" --defaults-file "$env:USERPROFILE\.restore-check.cnf" --expect-version auto
```

`--expect-version auto` compare la sauvegarde au **dépôt**, sans exiger qu'elles aient la même dernière migration : la base en ligne peut être en retard sur le dépôt (migrations écrites en local, pas encore appliquées en ligne). Le contrôle réussit si la dernière migration de la sauvegarde est une migration connue du dépôt **et** si toutes les migrations du dépôt jusque-là y sont enregistrées ; les migrations plus récentes du dépôt ne comptent pas comme des manques. `--expect-version <version>` exige, lui, cette dernière migration exacte. Le client `mysql` est lancé avec `--one-database` : un dump qui change de base (`USE`, `CREATE DATABASE`, export phpMyAdmin ou `--databases`) n'écrit que dans la base jetable.

Éprouvé le 05/11/2026 sur un vrai fichier : sauvegarde de la base d'essai `gic_agropelc_rp` par `backup-db.sh` (22 Mo, 130 tables, rotation et journal), restaurée par `restore-check.mjs` dans une base jetable de MySQL 8.4 (130 tables, 206 déclencheurs, comptes, migration `20261203100000` égale à celle du dépôt), base jetable supprimée. **Limite** : une sauvegarde de l'hébergement vient de MariaDB 11.8 ; la restaurer dans MySQL 8.4 peut échouer pour des écarts entre moteurs (collations, déclencheurs) sans que la sauvegarde soit mauvaise : l'essai le plus parlant se fait sur un MariaDB 11.x, et l'erreur du client est affichée telle quelle. Le premier essai sur une vraie sauvegarde de l'hébergement reste à faire par le porteur.

Contrôles sans serveur (`pnpm run check:deploy-kit`, aussi dans `pnpm run ci`) : `test-backup-rotate.mjs` (nommage, 14 jours, fins de mois, cinq copies sur un an, dernière gardée, ligne de commande), `test-restore-check.mjs` (base jetable, serveur local, clause `DEFINER`, flux binaire sans perte, lecture d'archive) et `test-mariadb-portability.mjs` : **contrôle statique de portabilité MariaDB** (AV-485) qui cherche dans `apps/server/src`, `db/seeds` et les migrations les constructions propres à MySQL que ni `mariadb-compat.mjs` ni `migrate.mjs` ne rattrapent (opérateurs `->`/`->>`, `MEMBER OF`, `ANY_VALUE`, `UUID_TO_BIN`, `FOR UPDATE OF`, `LATERAL`, alias de ligne d'un upsert, `FOR SHARE` écrit en SQL brut, `CAST(x AS JSON)` d'un autre opérande qu'un paramètre) ; une exception connue s'inscrit dans `ALLOWED` avec sa raison. Il ne remplace pas `compat-check.mjs`, qui essaie la vraie base à chaque livraison.

Le compteur du semis « N nouvelles règles sur 37 » (règles d'alerte) est exact depuis le 05/11/2026 (`db/seeds/run.ts` compte les lignes avant et après) ; la livraison du 05/11 affichait « 37 nouvelles règles sur 37 » à tort.

## Points d'attention

- Les mots de passe de base de données et de messagerie qui ont circulé dans les journaux d'Anti-Gravity (`~/.gemini/antigravity/brain/*/.system_generated/`) sont à changer **par le porteur lui-même** (le site n'est pas encore utilisé) ; aucun agent n'y touche, et aucun script de ce dossier n'en contient.
- La base de l'hébergement ne semble pas dédiée à GIC (l'historique montre des tables d'un site WordPress dans la même base, à confirmer) : préférer une base propre à GIC dès que l'hébergement le permet. Constaté le 07/11/2026 : la sauvegarde contient 159 tables, contre 130 pour le schéma de GIC (29 tables qui ne sont pas à GIC) ; elles sont sauvegardées avec le reste.
- Colonnes JSON : `compat-check.mjs` les relit **en objets** sur la base de l'hébergement, comme sous MySQL 8.4 (constaté le 30/10/2026) : aucun écart à ce sujet. Il afficherait « colonne JSON relue en texte » si cela changeait (le code qui lit une colonne JSON sans l'analyser s'en trouverait faussé : limites des droits, drapeaux, charges utiles). D'autres écarts de MariaDB restent possibles : à surveiller dans `stderr.log` et `console.log` (AV-485).
- Lire les erreurs du serveur : `~/domains/gic-agropelc.com/nodejs-app/stderr.log` (journal de Nest, erreurs de l'ordonnanceur) et `console.log` (une ligne JSON par erreur de l'API, avec le `correlation_id` renvoyé au client).
- Le premier démarrage après une mise à jour peut lever l'alerte `JOB_FAILED` si des tâches du serveur sont déjà passées `FAILED` dans les dernières 24 heures : c'est le comportement voulu (AV-469).
