# ADR-074 — Couche sémantique et explorateur : jeux déclarés, vues SQL en lecture, étendue exacte des lignes, mesures protégées, limites

- **Statut** : ACCEPTÉ (DÉDUIT, technique ; applique BR-ANA-004, 006, 007 et 009, D11 §8, NFR-12 et NFR-13 ; les choix métier sont AV-421 à AV-425, défauts paramétrables)
- **Date** : 14/10/2026 (numéro provisoire de la plage 070 à 079 de la session P9 ; révisé le même jour après la revue adverse de la conception)
- **Précise** : [ADR-070](ADR-070-architecture-de-p9-communication-et-analytics.md), [ADR-035](ADR-035-tableaux-d-analyse-avant-p9.md)
- **Questions liées** : AV-013, AV-086, AV-421 à AV-425

## Contexte

D11 demande une analyse flexible de type tableau croisé (filtrer, trier, grouper, choisir les colonnes, agréger, exporter, sauvegarder) sans requête libre (BR-ANA-006). Le dictionnaire `12-analytics.md` décrit treize jeux `f_*` et prévoit un filtre de périmètre « par une fonction de sécurité au niveau des lignes » ; MySQL n'en a pas.

Faits du code :
- `listConfinementAt` (`identity`, `rights-check.ts`) rend `{ siteIds, ownerUserIds }` ou `null`. C'est un **pré-filtre sur-ensemble** destiné à précéder `evaluateAccess` document par document : il ne porte aucune zone, et `null` signifie « aucun pré-filtre possible » (portée `ALL`, ou `SITE` ou `ZONE` sous une affectation globale, de zone ou d'équipe), jamais « tout est permis ». Il n'est pas utilisable seul sur un agrégat, où l'évaluation par ligne est impossible.
- L'octroi effectif d'une permission est l'intersection de sa portée maximale et du périmètre de l'affectation (`scope-evaluation.ts`, `resourceInGrantScope`) ; `OWN` exige le titulaire **et** le périmètre de l'affectation ; `TEAM` ne passe pas par l'affectation (`isWithinTeamScope`).
- `ReadScope` (`platform/read-scope.ts`) combine sites et personnes en ET, sans zone.
- Les tables sources portent déjà des colonnes de jour métier générées et indexées : `sales_sales.business_date`, `sales_sale_cancellations.applied_business_date`, `inventory_stock_moves.business_date`, ainsi que des colonnes équivalentes sur les encaissements, les dépenses, les mouvements de trésorerie et les pertes ; `inventory_cost_entries`, `crm_visits` et `fieldwork_work_sessions` n'en ont pas (index par utilisateur ou objet et instant).
- `inventory_stock_moves`, `inventory_stock_balances`, `inventory_cost_entries`, `finance_cash_movements`, `crm_visits` n'ont ni `site_id` ni colonne de zone : le site se déduit de l'emplacement, du compte ou de l'objet de coût.

## Décision

1. **Catalogue déclaratif** dans `packages/domain` (`analytics-catalog.ts`), version numérotée. Par jeu : code, vue SQL, permissions de lecture requises (toutes), colonnes de portée, dimensions (nom, type, colonne, libellé), mesures (nom, agrégat, expression, colonne de période, `protected`), filtres admis par type, tri admis, période par défaut. Le compilateur n'accepte que ce qui est déclaré : un jeu, une dimension, une mesure ou un filtre inconnu est `ANALYTICS_FIELD_UNKNOWN`.
2. **Vues SQL en lecture** `analytics_f_*`, créées par les migrations du module `analytics` (`SQL SECURITY INVOKER`, `gic_app` : `SELECT` seulement) sur les tables des modules propriétaires, en lecture ; aucune écriture dans une table d'autrui. Chaque vue :
   - expose `business_day` comme **alias de la colonne de jour métier générée** de la table source quand elle existe, et ne calcule `CONVERT_TZ(…, '+00:00', '+01:00')` (décalage fixe) que pour les tables qui n'en ont pas ;
   - expose les colonnes de portée selon le tableau ci-dessous, dérivées une fois dans la vue, pas par la requête de l'utilisateur ;
   - porte les jointures lourdes, pour que la requête de l'utilisateur reste un `SELECT … GROUP BY` sur une seule vue.

   | Jeu | Colonnes de portée (dérivation) |
   |---|---|
   | `f_sales_line`, `f_orders` | site = `site_id` du document ; zone = celle de la vente, celle du site pour une commande ; personne = le commercial, à défaut le vendeur (`GET /sales`) |
   | `f_payments` | site de l'encaissement ; personne = le receveur |
   | `f_stock_moves` | une ligne par mouvement ; site source et site destination ; titulaire d'un emplacement mobile ; visible si **l'une** des extrémités est dans l'étendue ; les emplacements virtuels (sans site) ne comptent pas |
   | `f_stock_balance` | site de l'emplacement ; titulaire d'un emplacement mobile |
   | `f_losses` | site de l'emplacement ; déclarant |
   | `f_prospecting` | zone du compte client (`crm_customers.zone_id`) ; personne = l'acteur de l'événement (acquéreur, auteur de la visite, titulaire à la conversion), comme `commercialEffort` ; une visite se lit par son auteur comme dans le module `crm`, mais un compte ou une conversion non par le titulaire courant que juge `GET /customers` (AV-491) |
   | `f_attendance` | zone déclarée au pointage (`declared_zone_id`) ; personne = `user_id` de la session ; règle fermée pour la portée de site |
   | `f_production_daily`, `f_costs` | site du lot de production ; pour un coût, site déduit de l'objet de coût (lot : site du lot ; frais généraux : le site lui-même) ; aucune portée par personne (les lectures de production ne jugent que le site) |
   | `f_expenses`, `f_cash` | site de la dépense ou du compte de trésorerie ; auteur de la dépense, titulaire du compte (à défaut son responsable) |
   | `f_purchases` | site du bon ou de la réception ; aucune portée par personne (les lectures des achats ne jugent que le site) |

   **Règle fermée** : un jeu dont aucune colonne de portée ne permet d'exprimer le type de portée de l'utilisateur ne rend aucune ligne pour celui-ci (jamais « tout »).
3. **Grain et dates.** Une ligne de `f_sales_line` est une ligne de vente ou une ligne d'annulation **appliquée** (`status = 'APPLIED'`), datée de `applied_at` (jour `applied_business_date`), comme `saleActivityArms` (`period-activity.ts`). Elle expose **deux** colonnes de date : `business_day` (jour de l'événement) et `sale_day` (jour de la vente d'origine, repris par la jointure pour une annulation). Chaque mesure déclare la colonne de période sur laquelle porte le filtre (`revenue`, `quantity` : `business_day` ; `net_by_sale_date` : `sale_day`) ; une requête qui mêle des mesures de colonnes de période différentes est refusée (`ANALYTICS_MIXED_PERIOD_BASIS`). La dimension « lot » n'est pas portée par `f_sales_line` : une ligne se répartit sur plusieurs mouvements `SALE` (un par lot), et le CA d'un lot reste donné par `lotRevenue` (AV-424). La mesure « nombre de ventes » compte les ventes distinctes non annulées en totalité à l'instant de lecture (KPI-COM-07), pas la somme des événements.
4. **Étendue exacte des lignes (BR-ANA-004).** Une fonction `resolveExactScope(executor, {userId, permission, at})` (fichier `analytics/application/scope/exact-scope.ts`, P9-14) rend une **union de prédicats** : `ALL`, ou une liste de clauses sur `site`, `zone` (avec descendantes) et `titulaire`. Elle ne se déduit pas de `listConfinementAt`. Elle énumère les univers finis (sites de la ferme, zones, utilisateurs) et appelle `evaluateAccess` pour : chaque site (ressource `{siteId}`), chaque site avec l'utilisateur comme titulaire (`{siteId, ownerUserId: soi}`), chaque zone (`{zoneId}`) et chaque utilisateur (`{ownerUserId}`). Le résultat est **sûr par construction** : tout élément retenu est visible par un octroi pour **toute** ressource portant ce seul attribut, donc la clause ne rend jamais plus que `evaluateAccess` ; les couples (périmètre, titulaire) que le droit exige sont couverts par des clauses conjonctives (révision P9-14). L'énumération est bornée (500 candidats par sorte, `truncated` le dit ; AV-423). Une fonction publique d'`identity` (`readScopeAt`) la remplacera sans changer le contrat (besoin B5, suivi §5). Une étendue qui ne se résout pas est **vide**, jamais `ALL`.
5. **Compilation** : le compilateur produit la clause `WHERE` de portée depuis l'union (`site IN (…)` OU `zone IN (…)` OU `titulaire IN (…)`, par clause) en plus des filtres de l'utilisateur ; l'étendue se compile en `WHERE` sur les colonnes de portée du catalogue (`analytics/application/scope/scope-sql.ts`, P9-14) ; `ReadScope` n'est pas touché (AV-423).
6. **Requête** : `POST /api/v1/analytics/query` reçoit une définition JSON (jeu, période, filtres, dimensions, mesures, tri, limite), validée par un schéma zod puis par le catalogue, et rend les lignes, `computed_at`, la fraîcheur (BR-ANA-005) et les identifiants des documents sources (ADR-075 §6). Le compilateur ne concatène jamais de texte de l'utilisateur ; les noms de colonne viennent du catalogue, les valeurs sont des paramètres.
7. **Mesures protégées** : toute mesure exprimée en valeur au coût — coût, marge, valeur de stock, valeur d'une perte, montants d'achat, montants de coût — est marquée `protected` et exige `inventory.valuation.read` (BR-ANA-004, RC-05). L'explorateur et les exports **refusent** la requête qui la nomme (`FORBIDDEN_MEASURE`) ; les tableaux la masquent (valeur `null`, ADR-035). Chaque mesure protégée est vérifiée contre la lecture HTTP du module qui la masque déjà (pertes, achats, production) : l'explorateur refuse exactement ce que la lecture masque. Un jeu dont toutes les mesures utiles sont protégées pour l'utilisateur est refusé par la même erreur (AV-422, AV-424).
8. **Limites (BR-ANA-006)** en paramètres `analytics.*` : 10 000 lignes affichées, 100 000 lignes exportées, 15 s d'exécution (`MAX_EXECUTION_TIME`), période détaillée de trois ans au plus (`PERIOD_TOO_LONG`). Le compilateur lit `LIMIT + 1` ; **le dépassement est une erreur** `QUERY_LIMIT_EXCEEDED` avec une suggestion d'affiner, jamais un résultat tronqué en silence ; un export qui lit plus de 100 000 lignes termine `FAILED` avec ce code (ADR-077). Le total d'une requête est calculé séparément, sans `GROUP BY`, et n'est pas rendu pour une mesure non additive (comptes distincts, moyennes, ratios). La période est obligatoire pour un jeu daté ; les jeux d'état (`f_stock_balance`) lisent l'instant.
9. **Index** : ceux des tables sources suffisent là où la table porte un jour métier indexé avec le site ; P9-13 ajoute, dans une migration de sa plage, les index manquants (coûts par date, visites et sessions par date, mouvements par emplacement et date), chacun justifié par le plan `EXPLAIN` de la requête qui le motive (ADR-078 §4). Aucune vue matérialisée.
10. **Audit** : chaque requête est journalisée (utilisateur, jeu, filtres, dimensions, mesures, nombre de lignes, durée) dans `analytics_query_log` ; un refus de droit ou de limite l'est aussi (RC-09, BR-AUD-009).

## Alternatives écartées

- **Requêtes SQL libres sur un schéma d'analyse** : contraire à BR-ANA-006, exposerait les colonnes personnelles et défierait le confinement.
- **Étendue tirée de `listConfinementAt`** : c'est un pré-filtre dont `null` ne dit rien ; sur un agrégat, aucun contrôle par ligne ne le rattrape.
- **Évaluation par ligne** : impossible sur un agrégat ; l'étendue exacte est calculée avant la requête.
- **Copie des faits dans des tables `analytics_*` alimentées par événements** : double source de vérité et rattrapage des opérations tardives ; palier 2 de la stratégie, à n'ouvrir que sur mesure (ADR-078).
- **Un seul jeu « tout-en-un »** : jointures coûteuses, grain ambigu.

## Conséquences

- Ajouter un jeu ou une mesure est une modification du catalogue, d'une vue et d'un test d'équivalence (ADR-075) : trois fichiers, pas de code de requête.
- La permission de lecture du domaine **est** l'accès au jeu : `analytics.explore` ouvre l'outil, pas les données.
- Le calcul d'étendue coûte au plus quelques centaines d'évaluations de droits en cache ; la tâche d'instantanés le mutualise (ADR-076).

## Révision du 22/10/2026 (P9-13)

- **Vues non modifiables.** Les treize vues sont créées `ALGORITHM = TEMPTABLE SQL SECURITY INVOKER` : un essai de P9-13 a montré qu'une vue fusionnée à table unique (`analytics_f_expenses`) laisse passer un `UPDATE` avec les droits de l'application sur la table de base, quel que soit le droit sur la vue (et une jointure se laisse écrire colonne par colonne). Une vue matérialisée à la lecture n'est pas modifiable ; la condition de période et de portée du compilateur est poussée dans la vue (constaté par `EXPLAIN` sur la base d'essai : l'optimiseur de MySQL pousse le filtre de jour et de site dans la lecture de la table source, dont les index servent ; rien ne le garantit au-delà de la version testée, P9-22 le remesure sur volume). Les essais du serveur lisent `INFORMATION_SCHEMA.VIEWS.IS_UPDATABLE` (`NO` pour les treize) et tentent `INSERT`, `UPDATE` et `DELETE` sur une colonne réelle de chaque vue.
- **Libellés constants.** Les colonnes `event_kind` portent explicitement la collation de la base (`utf8mb4_0900_as_cs`) : sans elle, la collation de la connexion qui crée la vue entre en conflit avec celle des paramètres de la requête (`Illegal mix of collations`).
- **Portée = celle du module propriétaire** (revue adverse de P9-13) : encaissements par le receveur ; ventes par le commercial, à défaut le vendeur (`owner_user_id`, comme `GET /sales`, et non « vendeur ou commercial » comme l'accueil) ; commandes par le commercial et la zone **du site** (non celle du client) ; prospection par l'acteur de l'événement seul (une visite se lit par son auteur : le titulaire ou l'acquéreur du compte n'en hérite pas) ; présences par la zone déclarée au pointage (la session porte `declared_zone_id`, contrairement à ce que ce document supposait) ; trésorerie par le titulaire du compte, à défaut son responsable. Le site couvre les droits de portée zone quand la zone de la ligne se déduit de celle du site ; les jeux dont la ligne porte sa propre zone (ventes : zone du client ou du pointage, parfois différente de celle du site ; commandes : zone du site) ou n'a pas de site (prospection, présences) ont une colonne de zone, que l'étendue exacte lit en propre (révision P9-14).
- **Mesures constatées, en attente, non justifiées** : les pertes et les dépenses portent ces trois sens dans des colonnes distinctes (`quantity_base`/`value_xaf` et `pending_*` ; `amount_xaf`, `pending_xaf`, `unjustified_xaf`), comme `lossValueSummary` et `expensesSummary` ; une perte rejetée et rendue n'est pas une perte. Les soldes de stock excluent les emplacements qui ne sont que la source ou le puits d'un mouvement (`location_type`), gardent le transit, les pertes en attente et l'à-livrer. Les achats ignorent les lignes annulées d'un bon et les bons en attente d'approbation. Les mouvements exposent `is_reversal` et `source_doc_type` ; le `move_type` d'une contre-écriture n'est pas toujours celui du mouvement qu'elle défait (consommation annulée : `CONSUMPTION_REVERSAL` ; réception annulée : `SUPPLIER_RETURN` ; production annulée : `PRODUCTION_INPUT` et `PRODUCTION_OUTPUT` échangés), d'où la dimension `is_reversal`. Les commandes sont datées de leur confirmation (KPI-COM-06) ; les conversions sans titulaire restent comptées. AV-490.
- **Pour le compilateur (P9-14)** : une somme ou un compte vide n'est pas un zéro (`SUM` rend `NULL` sur un groupe sans fait : `COALESCE(…, 0)`), mais une moyenne, un minimum ou un maximum vide reste `NULL` (la durée d'une session ouverte est inconnue, non nulle) ; `cost_xaf` et `margin_xaf` sortent en décimal (chaîne avec `mysql2`) ; `override` et `is_reversal` sont des entiers 0/1 ; les identifiants sont des `BINARY(16)` et les jours des `DATE` (à formater avec `DATE_FORMAT`) ; les filtres `NE` et `NOT IN` perdent les lignes à dimension vide (logique à trois valeurs) : **toujours** compilés avec `IS NULL OR`, sans liste de dimensions nullables à tenir (le catalogue ne porte pas la nullité ; sont nullables au moins `customer_id`, `customer_category_id`, `commercial_user_id`, `result`, `stock_lot_id`, `production_lot_id`, `building_id`, `cost_object_type`, `user_id` de prospection, les sites virtuels ou centraux).
- **Écarts entre fonctions publiques** : quand deux définitions coexistent dans le code, la vue suit la plus proche de la définition métier et l'écart est tracé (mortalité comptée : AV-486 ; valeur d'un solde : AV-487 ; remise et coût d'une annulation : AV-488 ; facturé et payé hors du jeu des achats : AV-489).
- **Index (§9).** Aucun index n'est ajouté par P9-13 : sur la base d'essai (au plus quelques dizaines de milliers de lignes par table) le plan `EXPLAIN` choisit le parcours complet avec ou sans index, et un essai d'index fonctionnel sur le jour métier calculé n'a pas été utilisé par l'optimiseur. Les index qu'un volume réel justifie (coûts, visites, sessions, commandes, réceptions : tables sans colonne de jour métier générée) sont ceux de P9-22, mesurés sur le volume de [ADR-078](ADR-078-charge-paliers-analytiques-et-retention.md).

- **Seconde revue adverse de P9-13 (22/10/2026).** Le disponible d'un solde est nul hors emplacement physique et les soldes entièrement à zéro sont omis, comme `GET /stock` ; la valeur et le solde sans filtre d'emplacement additionnent physique, transit, pertes en attente et à-livrer (`location_type`, AV-494). La trésorerie expose `is_reversal` ; entrées et sorties sont des flux bruts, virements et écarts de caisse compris (AV-494). Un bon de commande est daté de son approbation (AV-493). Un compte fusionné n'est compté ni à la création ni à la conversion (AV-492). Les achats, la production du jour et les coûts n'ont plus de portée par personne : les lectures des modules ne jugent que le site, et l'explorateur ne rend jamais plus qu'elles. Les comptes et les conversions se lisent par l'acteur de l'événement, non par le titulaire courant (AV-491).

## Révision du 22/10/2026 (P9-14)

- **Où et comment.** `resolveExactScope` et `scopeCondition(s)` vivent dans le module `analytics` (`application/scope/`, exportés par son API publique) ; l'étendue se compile directement en clause `WHERE` sur les colonnes de portée de la vue (`DatasetDefinition.scope`) : `ReadScope` n'est pas modifié et aucun mode « union » n'est ajouté. Le module `analytics` lit les API publiques d'`identity` (`evaluateAccess`, `listConfinementAt`, affectations actives) et d'`organization` (équipes, zones, sites) ; la règle de dépendances l'autorise.
- **Aucune combinaison non énumérable ne reste** (la grille des vingt couples portée maximale × affectation est complète). Une permission `OWN` sous une affectation de site ou de zone exige le couple (périmètre, soi) : clauses `SITES_AND_SELF` et `ZONES_AND_SELF`, essayées pour chaque site et zone candidats et retenues seulement si ni le périmètre seul ni soi seul ne suffisent (pas de clause redondante). Une permission `SITE` ou `ZONE` sous une affectation d'équipe ne juge que le titulaire : clauses `ANY_SITE_AND_PERSONS` et `ANY_ZONE_AND_PERSONS` (la ligne porte un site, ou une zone, **et** un membre de l'équipe affectée). Sous une affectation d'équipe, seuls les membres de l'équipe **affectée** comptent pour `SITE` et `ZONE` ; ceux d'une équipe dirigée ne comptent que pour `TEAM` (`isWithinTeamScope`).
- **Candidats.** Sites des affectations de site, sites des zones affectées et de leurs descendantes (`listZoneIdsWithDescendants`, `listSiteIdsInZones`), zones affectées et descendantes, soi, membres des équipes dirigées et de l'équipe de chaque affectation d'équipe (`scopeTeamId`). `listConfinementAt` n'est qu'une **source de candidats** (jamais un droit) : il rend `null` dès qu'un octroi est global ou de portée `SITE`/`ZONE` sous une affectation non-site, et les membres d'équipe sont alors repris explicitement. Un site, une zone « quelconque » est sondé par un identifiant bien formé qui n'existe pas (`SCOPE_PROBE_ID`) : permis ⇒ clauses `ANY_SITE` et `ANY_ZONE`.
- **Jeux à attributs partiels.** Un jeu qui ne porte pas le site, la zone ou la personne n'est jugé que sur les attributs qu'il porte (la ressource passée à `evaluateAccess` ne contient que ceux-là) ; la grille est rejouée pour les six projections (site, zone, personne, seuls ou deux à deux).
- **Zone propre d'une ligne (seconde revue de P9-13).** `evaluateAccess` déduit la zone d'une ressource de son site quand elle n'en porte pas, mais juge la zone de la ressource quand elle en porte une : une vente hors point de vente porte la zone du client ou du pointage, qui peut différer de celle de son site. Un site retenu par une affectation de zone n'est donc pas lisible « pour lui-même ». L'étendue sépare les sites lus pour eux-mêmes (jugés avec une zone inexistante : affectation de site, `SITES.ids`) de ceux lus par leur zone (`SITES.viaZoneIds`) et les zones lues sans exiger de site (`ZONES.ids`) de celles lues pour une ligne qui porte aussi un site (`ZONES.withSiteIds` : portée `SITE` sous une affectation de zone). Un jeu qui porte la zone de la ligne lit les sites « par leur zone » par cette zone ; un jeu sans colonne de zone les lit par le site. Les couples (site, soi) suivent la même séparation. La grille est rejouée sur des lignes dont la zone diffère de celle du site (quatre combinaisons rendaient des lignes à tort ou en omettaient avant la correction). Limite : une ligne dont la zone propre est vide, lue par le seul site d'une affectation de zone, n'est pas rendue (étendue plus étroite, jamais plus large) ; aucun jeu n'a de zone vide aujourd'hui (la zone d'une vente est obligatoire).
- **Plafond.** 500 candidats par sorte (`maxCandidates`) ; au-delà, les derniers par identifiant sont écartés (étendue plus étroite, jamais plus large) et `truncated` est vrai. Le compilateur le reprend d'un réglage `analytics.scope_max_candidates` (ajouté avec lui, P9-14 (2/4)).

## Révision du 22/10/2026 (P9-14, compilateur)

- **Compilateur** (`analytics/application/query/compile-exploration.ts`) : un plan déjà validé par le domaine devient un `SELECT` sur la vue du jeu. Aucun texte de l'utilisateur n'entre dans le SQL : colonnes, vue et agrégats viennent du catalogue, les valeurs sont des paramètres, la direction d'un tri est l'une de deux constantes, les alias (`d0…`, `m0…`) sont ceux du compilateur. La période borne la colonne de date **commune aux mesures** (`sale_day` pour « net par date de vente »). `NE` se compile toujours `IS NULL OR … <>` (la logique à trois valeurs perdrait les lignes à dimension vide) ; `CONTAINS` échappe `%`, `_` et son caractère d'échappement (`!`, jamais la barre oblique inverse que MySQL interprète). Un jour sort en `AAAA-MM-JJ` (`DATE_FORMAT`), un identifiant en UUID, un décimal en nombre ; `SUM` et `COUNT` valent 0 sur un groupe sans fait, une moyenne ou un maximum vide reste `NULL`.
- **Ordre déterministe** : le tri demandé, puis les dimensions dans l'ordre.
- **Total** : requête séparée sur les mêmes lignes (période, filtres, étendue), sans `GROUP BY`, seulement si toutes les mesures sont additives ; sans dimension, l'unique ligne en est le total.
- **Limites en erreur** (`run-exploration.ts`) : le compilateur lit `LIMIT + 1`. Au-delà du plafond de lignes (`analytics.query_max_rows`, 10 000) : `ExplorationLimitError` `rows` (422), jamais une troncature. Une **limite demandée par l'utilisateur, plus petite que le plafond, est un « premier N » voulu** : les N premières lignes sont rendues sans erreur, le total portant sur toutes les lignes. La durée (`analytics.query_max_execution_ms`, 15 000) est un indice d'optimiseur `MAX_EXECUTION_TIME` ; son dépassement (erreur 3024) devient l'erreur `time` (422). Les deux sont des `QUERY_LIMIT_EXCEEDED` de détail `limit`.
- **Concurrence par utilisateur** (`query-slots.ts`) : au plus `analytics.query_max_concurrent_per_user` (2) requêtes simultanées, tous processus du serveur confondus, par des **verrous nommés MySQL** (`GET_LOCK(nom, 0)`, un par rang et par utilisateur) tenus par la connexion qui exécute la requête, rendus en fin de requête réussie ou en erreur (et à la perte de la connexion). Tous les rangs tenus : 429 `QUERY_LIMIT_EXCEEDED`, détail `concurrency`.
- **Instantané** : les lignes et le total se lisent dans une transaction `REPEATABLE READ` en lecture seule (un fait validé entre les deux ne les rend pas incohérents ; une écriture y est refusée).
- **Réglages** (`organization.system_settings`, semés) : `analytics.query_max_rows` 10 000, `analytics.query_max_execution_ms` 15 000, `analytics.query_max_period_days` 1 096, `analytics.query_max_concurrent_per_user` 2, `analytics.scope_max_candidates` 500 ; une valeur absente ou mal formée retombe sur ce défaut.
- **Route** (P9-14 (3/4), `analytics-api/analytics-explorer.controller.ts`) : l'ordre des contrôles est celui d'une fuite minimale : (1) `analytics.explore` ; (2) la vue sauvegardée éventuelle (visible du propriétaire et des rôles destinataires, sinon 404 opaque audité) ; (3) **chaque permission de lecture du jeu**, avant toute information sur ses champs (403 `FORBIDDEN` audité et journalisé) ; (4) la définition contre le catalogue, les limites et le droit de valorisation (400, 403 `FORBIDDEN_MEASURE` audité, 409 `VIEW_OUTDATED` pour une vue dont un champ a disparu) ; (5) l'étendue exacte de **chaque** permission de lecture du jeu, et de `inventory.valuation.read` quand une mesure au coût est demandée (intersection) ; (6) le calcul sous les limites (422, 429). Le catalogue ne liste que les jeux dont le lecteur détient toutes les permissions. La réponse porte `scopeTruncated` (étendue coupée par le plafond de candidats : résultat plus étroit que le droit, jamais plus large) et la fraîcheur : appareils actifs des points de vente que l'étendue de la première permission atteint, dont ceux sans contact depuis `analytics.freshness_warning_hours` (`explorer-freshness.ts`).
- **Journal** (`query-log.ts`) : une ligne de `analytics_query_log` par requête, refus et limites compris (jeu, définition reçue, période résolue, version du catalogue, résultat `OK`, `REFUSED`, `LIMIT` ou `ERROR`, code, lignes, durée).

## Tests

Catalogue valide (toutes colonnes existent dans la vue ; migration descendante) ; **grille d'étendue** : chaque portée maximale (`ALL`, `SITE`, `ZONE`, `TEAM`, `OWN`) sous chaque affectation (globale, site, zone, équipe) — pour un échantillon de lignes, la clause compilée ne rend **jamais** une ligne que `evaluateAccess` refuse, et rend celles qu'il accepte hors combinaisons non énumérables ; étendue vide ; mesures protégées (refus exact = masquage de la lecture HTTP) ; limites (lignes, durée, période, `LIMIT + 1`) ; injection (nom de champ, tri, valeur hostiles) ; mélange de colonnes de période ; équivalence avec les fonctions publiques (ADR-075) ; mutations sur la clause de portée.
